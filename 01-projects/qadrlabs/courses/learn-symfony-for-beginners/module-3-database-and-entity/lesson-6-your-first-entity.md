## 1. Before You Begin

In the previous lesson, we created the `Entry` and `User` entities and ran migrations to build the corresponding database tables. But having tables in a database means nothing if your PHP code does not know how to talk to them. This lesson answers that question using Doctrine's Repository pattern.

Doctrine separates the concern of representing data from the concern of fetching it. Entities are plain PHP objects: they hold data and expose it through getters and setters. Repositories are query classes: they ask the database for data on behalf of the controller.

This lesson updates the `EntryController` to use the real database instead of the hardcoded array, updates the Twig template to work with entity objects instead of plain arrays, and loads seed data into the database using Doctrine Fixtures so there is something to see in the browser.

### What You'll Build

By the end of this lesson, the entries listing page will show real data fetched from the database. You will also have a test user and three seed entries created via Doctrine Fixtures.

## 2. The Repository Pattern

When Doctrine generated the `Entry` entity in Lesson 5, it also created a companion class: `src/Repository/EntryRepository.php`. This class is the correct place for all database queries related to entries.

### Step 1: Understand the Repository

Open `src/Repository/EntryRepository.php`:

```php
<?php

namespace App\Repository;

use App\Entity\Entry;
use Doctrine\Bundle\DoctrineBundle\Repository\ServiceEntityRepository;
use Doctrine\Persistence\ManagerRegistry;

/**
 * @extends ServiceEntityRepository<Entry>
 */
class EntryRepository extends ServiceEntityRepository
{
    public function __construct(ManagerRegistry $registry)
    {
        parent::__construct($registry, Entry::class);
    }

    // Commented-out example methods generated by make:entity...
}
```

The generated file also contains two commented-out example methods, `findByExampleField()` and `findOneBySomeField()`. They are only templates showing how a custom query looks, so you can leave them as they are or delete them. The `@extends` comment above the class tells code editors and static analysis tools that this repository returns `Entry` objects.

`EntryRepository` extends `ServiceEntityRepository`, which provides a set of ready-made query methods. By extending this parent class, `EntryRepository` inherits `find($id)`, `findAll()`, `findBy([...])`, and `findOneBy([...])` without writing a single query yourself. You can also add custom methods to this class when the built-in options are not flexible enough.

`parent::__construct($registry, Entry::class)` tells the parent class which entity this repository is for. The `$registry` is Doctrine's connection manager, injected by Symfony automatically.

## 3. Updating the Controller

Now update the controller to stop using the hardcoded array and start asking the repository for real data from the database.

### Step 1: Update EntryController

Replace the hardcoded array in `index()` with a repository query. The complete `src/Controller/EntryController.php` now looks like this:

```php
<?php

namespace App\Controller;

use App\Repository\EntryRepository;
use Symfony\Bundle\FrameworkBundle\Controller\AbstractController;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\Routing\Attribute\Route;

class EntryController extends AbstractController
{
    #[Route('/entries', name: 'entry_index')]
    public function index(EntryRepository $entryRepository): Response
    {
        $entries = $entryRepository->findBy([], ['createdAt' => 'DESC']);

        return $this->render('entry/index.html.twig', [
            'entries' => $entries,
        ]);
    }
}
```

`EntryRepository $entryRepository` in the method signature uses Symfony's dependency injection. When Symfony calls `index()`, it automatically creates an `EntryRepository` instance and passes it in. You never need to manually write `new EntryRepository(...)`. This behavior is available for any service registered in Symfony's container, which includes all repository classes.

`findBy([], ['createdAt' => 'DESC'])` fetches all entry records from the database. The first argument is a criteria array used to filter results. An empty array `[]` means no filter, so all entries are returned. The second argument is a sorting array: entries are sorted by `createdAt` in descending order, so the newest appear first.

For now, this fetches entries from all users. Once the login system is in place in Lesson 10, you will add `['user' => $this->getUser()]` as a filter to scope entries to the logged-in user only.

## 4. Updating the Twig Template

The entries are now Doctrine entity objects rather than plain PHP arrays. This requires a small adjustment to how the template accesses their data.

### Step 1: Update the Entry Index Template

Replace the contents of `templates/entry/index.html.twig`:

```html
<!DOCTYPE html>
<html lang="en">
<head>
    <meta charset="UTF-8">
    <meta name="viewport" content="width=device-width, initial-scale=1.0">
    <title>My Entries - Catatku</title>
    <script src="https://unpkg.com/@tailwindcss/browser@4"></script>
</head>
<body class="bg-gray-50">

    <nav class="bg-white border-b border-gray-200 px-6 py-4">
        <h1 class="text-xl font-bold text-gray-900">Catatku 📓</h1>
    </nav>

    <div class="max-w-2xl mx-auto mt-8 px-4">
        <div class="flex items-center justify-between mb-6">
            <h2 class="text-lg font-semibold text-gray-900">My Entries</h2>
            <a href="/entries/create" class="bg-gray-900 text-white text-sm px-4 py-2 rounded-lg hover:bg-gray-700">
                + Write New Entry
            </a>
        </div>

        {% if entries is empty %}
            <div class="text-center py-16 text-gray-400">
                <p class="text-5xl mb-4">📓</p>
                <p class="font-medium text-gray-500">No entries yet</p>
                <p class="text-sm mt-1">Start writing your first entry!</p>
            </div>
        {% else %}
            {% for entry in entries %}
                <div class="bg-white rounded-xl border border-gray-200 p-5 mb-4">
                    <h3 class="font-semibold text-gray-900 mb-1">{{ entry.title }}</h3>
                    <p class="text-xs text-gray-400 mb-3">{{ entry.createdAt|date('d F Y') }}</p>
                    <p class="text-sm text-gray-600 line-clamp-2">{{ entry.content }}</p>
                </div>
            {% endfor %}
        {% endif %}
    </div>

</body>
</html>
```

`{{ entry.title }}` accesses entity data using Twig's dot notation. When `entry` is a Doctrine entity object (not a plain array), Twig automatically calls the getter method `$entry->getTitle()` behind the scenes. The same applies to `entry.content` and `entry.createdAt`. You do not need to change `entry.title` into `entry.getTitle()` in Twig. The dot notation handles both array keys and object method calls transparently.

`{{ entry.createdAt|date('d F Y') }}` uses Twig's built-in `date` filter to format the `\DateTimeImmutable` object into a human-readable string like `"06 April 2026"`. The format string `'d F Y'` means day, full month name, and four-digit year. Without this filter, Twig would attempt to convert the object directly to a string, which would either fail or display an unreadable internal representation.

## 5. Seeding Data with Doctrine Fixtures

Before you can see real entries in the browser, you need some data in the database. Doctrine Fixtures is the standard tool for this.

### Step 1: Install the Fixtures Bundle

Run the following command to install the package as a dev dependency:

```bash
composer require --dev doctrine/doctrine-fixtures-bundle
```

Using `--dev` means this package is only installed in development. It will not be included when you deploy to production, which keeps the production build lean.

The bundle's Flex recipe also creates a starter file at `src/DataFixtures/AppFixtures.php` with an empty `load()` method. You will replace its contents in the next step.

### Step 2: Create the AppFixtures Class

Replace the contents of `src/DataFixtures/AppFixtures.php` with the following:

```php
<?php

namespace App\DataFixtures;

use App\Entity\Entry;
use App\Entity\User;
use Doctrine\Bundle\FixturesBundle\Fixture;
use Doctrine\Persistence\ObjectManager;
use Symfony\Component\PasswordHasher\Hasher\UserPasswordHasherInterface;

class AppFixtures extends Fixture
{
    public function __construct(
        private UserPasswordHasherInterface $passwordHasher,
    ) {}

    public function load(ObjectManager $manager): void
    {
        $user = new User();
        $user->setName('Budi');
        $user->setEmail('budi@example.com');
        $user->setPassword($this->passwordHasher->hashPassword($user, 'password123'));
        $manager->persist($user);

        $entries = [
            ['My first entry', 'This is my very first journal entry. Feels great to get started!', '-3 days'],
            ['Learning Symfony', 'Today I learned about Doctrine ORM. The Repository pattern keeps things clean.', '-2 days'],
            ['Weekend plans', 'Planning to finish the Symfony course this weekend and maybe start a side project.', '-1 day'],
        ];

        foreach ($entries as [$title, $content, $writtenAt]) {
            $entry = new Entry();
            $entry->setTitle($title);
            $entry->setContent($content);
            $entry->setCreatedAt(new \DateTimeImmutable($writtenAt));
            $entry->setUser($user);
            $manager->persist($entry);
        }

        $manager->flush();
    }
}
```

`AppFixtures` extends `Fixture` and implements a single `load()` method. Inside it, you create entity objects just like you would in production code. `$manager->persist($entity)` marks an entity as "pending": Doctrine knows it needs to be saved but has not executed any SQL yet. `$manager->flush()` at the end sends all pending SQL operations to the database in a single transaction. This separation of marking and executing gives you full control over the order of operations and ensures that all inserts either succeed together or fail together.

Each entry row has a third value, such as `'-3 days'`. `new \DateTimeImmutable('-3 days')` creates a date three days in the past, and `setCreatedAt()` overwrites the date that the `Entry` constructor set. Without it, all three entries would be created in the same second and the "newest first" sorting would have nothing to sort by.

The `UserPasswordHasherInterface` is injected through the constructor. It hashes the password using the algorithm configured in `security.yaml`. Passwords must always be hashed before storage. Storing plain text passwords is a serious security vulnerability.

### Step 3: Run the Fixtures

```bash
php bin/console doctrine:fixtures:load
```

Type `yes` when prompted.

Output:

```text

 Careful, database "db_catatku" will be purged. Do you want to continue? (yes/no) [no]:
 > yes

   > purging database
   > loading App\DataFixtures\AppFixtures
```

This command clears all existing data in the database and then runs `AppFixtures::load()`. After it completes, the database contains one user (Budi) and three journal entries linked to that user.

### Step 4: View the Result

Open `http://localhost:8080/entries`. You should see three entries displayed from the real database, sorted by creation date with the newest first: "Weekend plans" (one day ago) at the top and "My first entry" (three days ago) at the bottom.

## 6. Common Repository Methods

The repository object provides a set of built-in query methods that cover most common use cases. Understanding when to use each one will save you from writing unnecessary custom queries.

Here is an overview of the most frequently used methods:

```php
$repository->find($id);
$repository->findAll();
$repository->findBy(['user' => $user], ['createdAt' => 'DESC']);
$repository->findOneBy(['email' => 'budi@example.com']);
```

`find($id)` retrieves a single entity by its primary key. If no record exists with that ID, it returns `null`. `findAll()` returns every record in the table with no filtering or sorting. `findBy($criteria, $orderBy)` fetches records matching the criteria array, optionally sorted. `findOneBy($criteria)` returns the first matching record or `null` if none is found.

For queries that are more complex than these methods support, you can add custom methods to the repository class using Doctrine's QueryBuilder. You will see this in later lessons when scoping entries by user.

## 7. Fix the Errors in Your Code

**Error 1: Calling a method on null because fixtures have not been loaded.**

When you first switch the controller to use the repository, the database is empty. The template tries to loop over an empty collection, which is fine. But if any part of the code assumes the collection has items, you get errors.

```php
// Wrong: assumes $entries is not empty, crashes if it is
$firstEntry = $entries[0];

// Correct: check that the array has items before reading one
$firstEntry = $entries[0] ?? null;
```

In templates, the same check is `{% if entries is empty %}`, which the entries template already uses.

After switching from a hardcoded array to the repository, always load fixtures with `php bin/console doctrine:fixtures:load` before testing. An empty database is not a bug, but code that does not handle an empty result gracefully is.

**Error 2: Accessing array keys on entity objects.**

After switching from a plain PHP array to a Doctrine entity, you cannot use array syntax to access properties.

```twig
{# Wrong: entry is now an object, not an array #}
{{ entry['title'] }}

{# Correct: use dot notation for both arrays and objects #}
{{ entry.title }}
```

Twig's dot notation works for both PHP arrays and objects. When you used a hardcoded array in Lesson 3, `entry.title` accessed the `'title'` key. Now that `entry` is a `Entry` object, `entry.title` automatically calls `$entry->getTitle()`. No template changes are needed if you were already using dot notation.

**Error 3: Forgetting `persist()` before `flush()`.**

`flush()` only saves entities that have been registered with `persist()`. Calling `flush()` on an entity that was never persisted does nothing.

```php
// Wrong: entity is created but never registered with Doctrine
$entry = new Entry();
$entry->setTitle('Test');
$manager->flush();  // nothing happens

// Correct: persist first, then flush
$entry = new Entry();
$entry->setTitle('Test');
$manager->persist($entry);
$manager->flush();
```

`persist()` marks the entity as "managed" by Doctrine. `flush()` then executes the SQL for all managed entities with pending changes. If you call `flush()` without `persist()` on a new entity, Doctrine has no record of it and will not insert it.

## 9. Solutions

**Solution for Exercise 1:**

Add a `findLatestByUser()` method and import the `User` class. The complete `src/Repository/EntryRepository.php` looks like this (the commented-out example methods are removed to keep it short):

```php
<?php

namespace App\Repository;

use App\Entity\Entry;
use App\Entity\User;
use Doctrine\Bundle\DoctrineBundle\Repository\ServiceEntityRepository;
use Doctrine\Persistence\ManagerRegistry;

/**
 * @extends ServiceEntityRepository<Entry>
 */
class EntryRepository extends ServiceEntityRepository
{
    public function __construct(ManagerRegistry $registry)
    {
        parent::__construct($registry, Entry::class);
    }

    /**
     * @return Entry[]
     */
    public function findLatestByUser(User $user, int $limit = 5): array
    {
        return $this->findBy(
            ['user' => $user],
            ['createdAt' => 'DESC'],
            $limit
        );
    }
}
```

`findBy()` accepts four arguments: criteria, ordering, limit, and offset. Passing `$limit` as the third argument tells Doctrine to return at most that many records. The `User $user` type hint ensures only a valid User object can be passed. You can call this custom method from any controller that has access to the `EntryRepository` via dependency injection.

**Solution for Exercise 3:**

In `templates/entry/index.html.twig`, change:

```twig
{{ entry.createdAt|date('d F Y') }}
```

To display in ISO format:

```twig
{{ entry.createdAt|date('Y-m-d') }}
```

The `|date()` filter accepts any format string compatible with PHP's `date()` function. `'Y-m-d'` produces output like `2026-04-06`. `'d/m/Y'` produces `06/04/2026`. The same filter works on any `\DateTime` or `\DateTimeImmutable` object. Reload the browser after changing the format string to see the updated display.
