## 2. The Anatomy of fun main

The single most important line in any Kotlin program is the one that declares the entry point. Every Kotlin application starts execution at a function called `main`, and understanding what each piece of that declaration means is essential before we go further.

### Step 1: Read the Existing main Function

Open `src/main/kotlin/Main.kt` from Lesson 2. The file should contain something close to:

```kotlin
fun main() {
    println("Hello, Catatku!")
}
```

(If you modified this in Lesson 2's exercises, restore it to roughly this shape so we have a clean starting point.) That is a complete Kotlin program. Let us walk through each piece.

The keyword `fun` declares a function. Kotlin uses `fun` rather than `function` (JavaScript), `def` (Python), or `void` (C/Java/C++) because brevity is a deliberate design choice. Every function declaration in Kotlin starts with `fun`, no exceptions. The name `main` is the function's name. The runtime looks specifically for a function named `main` to start the program; if you renamed it to anything else, the program would compile but would not have an entry point and the application plugin would refuse to run it.

The empty parentheses `()` indicate that this function takes no parameters. We will see in a moment that you can also write `fun main(args: Array<String>)` to receive command-line arguments, but for programs that do not need them, the empty form is preferred. The curly braces `{ ... }` enclose the function's body, the actual code that runs when the function is called. Inside the body, each statement is on its own line. Kotlin does not require semicolons at the end of statements (unlike Java or C), although you can use them if you want; the linebreak does the same job.

Inside the body is `println("Hello, Catatku!")`. `println` is a built-in function from the Kotlin standard library that prints its argument to the console followed by a newline. The argument is the string `"Hello, Catatku!"`, enclosed in double quotes. Strings in Kotlin always use double quotes; single quotes are reserved for individual characters (the `Char` type), which is a small difference from Python but matches Java's convention.

That is every part of the line. Once you can read each piece without thinking, the rest of the language builds on this same vocabulary.

### Step 2: Add Command-Line Arguments

Modify the function signature to accept command-line arguments:

```kotlin
fun main(args: Array<String>) {
    println("Hello, Catatku!")
    println("Number of arguments: ${args.size}")
}
```

The new parameter `args: Array<String>` says "this function takes one parameter named `args` of type `Array<String>`". The `Array<String>` is Kotlin's way of writing "an array of strings", with the element type in angle brackets after `Array`. When you run this version, the runtime fills `args` with whatever command-line arguments you passed when starting the program. From the IntelliJ run button you typically pass nothing, so `args.size` is 0.

Save the file and run it (click the green triangle next to `fun main`).

Output:

```text
Hello, Catatku!
Number of arguments: 0
```

To pass actual arguments, you can either run the program from the terminal with `./gradlew run --args="hello world"`, or in IntelliJ, click the Run dropdown, choose "Edit Configurations", and add `hello world` to the "Program arguments" field. After saving the configuration and rerunning, the program counts two arguments.

Output:

```text
Hello, Catatku!
Number of arguments: 2
```

We will use `args` heavily in Lesson 18 when Catatku starts processing real commands. For now, just note that `main` can either take no parameters or take an `Array<String>` of command-line arguments, and Kotlin lets you pick whichever you need.

### Step 3: Notice What Is Not There

Compare the Kotlin version to the equivalent Java entry point:

```java
// Java
public class Main {
    public static void main(String[] args) {
        System.out.println("Hello, Catatku!");
    }
}
```

Kotlin removes a lot of ceremony. There is no enclosing class declaration, because Kotlin allows top-level functions. There is no `public` or `static` keyword, because top-level functions are public by default and the concept of "static" does not apply at the top level. There is no `void` return type, because Kotlin uses `Unit` for "no useful return" and infers it when omitted. There is no `String[]` versus `String...` distinction; Kotlin has `Array<String>` and `vararg`, both of which are clearer once you know them. The argument type is required (Kotlin will not infer parameter types), but the `Array<String>` is a single readable phrase rather than `String[] args` with the brackets attached to the type.

These differences are typical of Kotlin compared to Java: the same logical operation is shorter, with less boilerplate, while remaining statically typed. The savings on `main` alone are small, but the same kind of saving compounds across thousands of lines of code in a real project.

## 3. Printing to the Console

Output is one of the first things every programmer needs, and Kotlin provides a small set of built-in functions for it. The most common are `println` (which adds a newline) and `print` (which does not).

### Step 1: Compare println and print

Replace the body of `main` with a small experiment:

```kotlin
fun main() {
    print("Hello ")
    print("Catatku ")
    println("user!")
    println("This is a separate line.")
}
```

Save and run.

Output:

```text
Hello Catatku user!
This is a separate line.
```

Notice that the three `print` calls all wrote to the same line because none of them ended with a newline. Only when `println` was called did the cursor advance to the next line. After that, each subsequent `println` produced its own line.

The two functions exist because both behaviors are sometimes wanted. `println` is by far the more common one because most output you produce should end with a newline. `print` is useful when you want to build a line in pieces, like printing a progress message followed by a percentage or a status indicator. Catatku will use `println` for almost everything, with `print` reserved for the rare case where partial-line output makes sense.

### Step 2: Print Different Types

`println` accepts not just strings but values of any type. Kotlin automatically converts the value to a string before printing.

```kotlin
fun main() {
    println("A string")
    println(42)
    println(3.14)
    println(true)
    println('A')
    println(null)
}
```

Save and run.

Output:

```text
A string
42
3.14
true
A
null
```

Each value is converted to a sensible string representation. Strings print as themselves, numbers print as their numeric value, booleans print as "true" or "false", characters print as the single character (without surrounding quotes), and `null` prints as the literal word "null". The conversion uses each type's `toString` method, which we will see in detail in Lesson 9 when we cover classes.

For complex values like collections or objects, the default `toString` may not be very readable, but Kotlin makes it easy to override `toString` for your own types so that printing them produces something useful. Data classes (Lesson 10) get a sensible `toString` automatically, which is one reason data classes are so pleasant to work with.

### Step 3: Use println to Trace Program Flow

A common debugging technique is sprinkling `println` calls throughout your code to see what is happening. Even though Kotlin has a real debugger built into IntelliJ, `println` debugging is still the fastest way to answer simple "is this code being reached?" questions.

```kotlin
fun main() {
    println("Start of program")
    val name = "Catatku"
    println("Set up name as: $name")
    println("End of program")
}
```

Save and run.

Output:

```text
Start of program
Set up name as: Catatku
End of program
```

The three `println` calls produce a trace of execution. The middle one uses a string template (introduced in Section 4 below) to embed the value of `name` into the output. This style is incredibly useful when you are confused about why a piece of code is or is not behaving the way you expect; just sprinkle `println` calls and watch the output to see what actually happens versus what you assumed would happen.

We will rely on this style throughout the course, especially in early lessons, because seeing output is the most direct feedback loop in programming.

## 4. String Templates

Kotlin's string templates are one of the small features that make daily code dramatically more pleasant. The syntax is `"$variable"` or `"${expression}"` inside a string, and at runtime Kotlin substitutes the value into the string at the marked position. This replaces explicit concatenation with `+` and the various `String.format` patterns that Java code is full of.

### Step 1: Use Simple Variable Substitution

Try this small example:

```kotlin
fun main() {
    val name = "Reader"
    val course = "Kotlin"
    println("Hello $name! Welcome to the $course course.")
}
```

Save and run.

Output:

```text
Hello Reader! Welcome to the Kotlin course.
```

The `$name` inside the string was replaced by the value of the `name` variable, and the `$course` was replaced by the value of `course`. The substitution happens at runtime: Kotlin's compiler generates code that calls `toString` on each substituted value and concatenates everything into the final string. This is more efficient than naive concatenation and dramatically more readable than the equivalent Java code that would use `+` between literal strings and variables.

Note that we used `val` to declare the variables, which we will cover in Lesson 4. For now, treat `val name = "Reader"` as "create a constant named `name` whose value is the string `Reader`".

### Step 2: Use Expression Substitution

Sometimes you want to embed something more complex than a single variable. The `${expression}` syntax (with curly braces) lets you put any expression inside the string.

```kotlin
fun main() {
    val firstName = "Ada"
    val lastName = "Lovelace"
    val birthYear = 1815
    println("Full name: ${firstName} ${lastName}")
    println("Length of last name: ${lastName.length}")
    println("Approximate age in 2026: ${2026 - birthYear}")
}
```

Save and run.

Output:

```text
Full name: Ada Lovelace
Length of last name: 8
Approximate age in 2026: 211
```

Three things happened. The first line shows that `${firstName}` is equivalent to `$firstName` for simple variable references; the curly braces are not needed but are not wrong either. The second line shows `${lastName.length}`, which calls the `.length` property on the `lastName` string and embeds the result. The third line shows `${2026 - birthYear}`, an arithmetic expression that gets evaluated and the result substituted.

The general rule is that `$variable` works for a single variable name and `${anything}` works for anything else. When in doubt, use the curly-brace form; the small extra typing makes the boundaries of the expression unambiguous, and it works for both cases.

### Step 3: Mix Strings and Templates

String templates compose with the rest of Kotlin's expression syntax. Here is a slightly more elaborate example that previews what Catatku's output will eventually look like:

```kotlin
fun main() {
    val taskId = 1
    val description = "Buy groceries"
    val isDone = false
    val marker = if (isDone) "[x]" else "[ ]"
    println("$marker $taskId. $description")
}
```

Save and run.

Output:

```text
[ ] 1. Buy groceries
```

Notice the line `val marker = if (isDone) "[x]" else "[ ]"`. This is `if` as an expression, which we will cover properly in Lesson 5. For now, observe that the `if` here returns a value (either `"[x]"` or `"[ ]"`) that gets stored in `marker`, and that string is then embedded in the final printed line via `$marker`. The final output line looks exactly like the format Catatku will use for its task list.

This is what happens when several Kotlin idioms compose: each piece is small, but together they let you express common patterns concisely. Compare to the Java equivalent, which would use a chained ternary, explicit `String.format`, or a `StringBuilder`, all of which are noisier than the Kotlin version. The savings come from string templates plus expression-form `if` plus type inference all working together.

## 5. Comments

Comments are notes you add to code that the compiler ignores. They exist purely for human readers (including future you, six months from now, who will not remember why the code looks the way it does). Kotlin supports two comment styles, the same two as Java and most C-family languages.

### Step 1: Single-Line Comments

A single-line comment starts with `//` and continues to the end of the line. Everything after the `//` is ignored by the compiler.

```kotlin
fun main() {
    // This is a single-line comment.
    println("Hello, Catatku!")  // Comments can also follow code on the same line.
    // The next line is a comment, so it does not run:
    // println("This will not appear in the output.")
}
```

Save and run.

Output:

```text
Hello, Catatku!
```

Three observations. Single-line comments can stand alone on a line or follow code on the same line. The compiler entirely ignores comment text, so commented-out code is genuinely not run; this is useful for temporarily disabling lines without deleting them. Comments can contain any characters, including code-like text, and the compiler will not try to interpret them.

### Step 2: Multi-Line Comments

A multi-line comment starts with `/*` and ends with `*/`. Everything between is ignored.

```kotlin
fun main() {
    /*
     * This is a multi-line comment.
     * It can span as many lines as you want.
     * Each line starts with " *" by convention but does not have to.
     */
    println("Hello, Catatku!")
    
    /* You can also write a multi-line comment on a single line. */
    println("Done.")
}
```

Save and run.

Output:

```text
Hello, Catatku!
Done.
```

Multi-line comments are useful for longer explanations that would be awkward as a series of single-line `//` comments. The convention of starting each interior line with `*` is purely cosmetic; the compiler does not require it, but it makes the boundaries of the comment block visually clear and is what most code style guides recommend.

Unlike in Java, Kotlin's multi-line comments can be nested. That is, you can put `/* ... */` inside another `/* ... */` and the compiler will correctly track the nesting. This is occasionally useful when you want to comment out a block of code that itself contains multi-line comments, which is awkward in languages where comment delimiters do not nest. We rarely need this feature in practice, but it is good to know it exists.

### Step 3: KDoc Comments

A third comment style, KDoc, looks like a multi-line comment that starts with `/**` (two asterisks). KDoc is a documentation format similar to Javadoc, used for documenting public APIs.

```kotlin
/**
 * Greets the user with their name.
 *
 * @param name The name of the person to greet.
 */
fun greet(name: String) {
    println("Hello, $name!")
}

fun main() {
    greet("Reader")
}
```

Save and run.

Output:

```text
Hello, Reader!
```

KDoc comments appear above functions, classes, and properties. They support special tags like `@param` (for documenting parameters), `@return` (for documenting return values), and `@throws` (for documenting exceptions). IntelliJ uses these comments to generate hover-tooltip documentation when you mouse over a function name elsewhere in the code, and tools like Dokka can extract them into a website similar to Javadoc-generated HTML.

For this course we will write simple comments to explain things, but you should be aware that KDoc exists and is the convention for documenting library code. When you start writing code that other people will use, learning the KDoc tags is a small investment with a large payoff in code clarity.

## 7. Fix the Errors in Your Code

Three syntax mistakes are common in early Kotlin code.

**Error 1: Forgetting the Curly Braces Around an Expression in a Template**

```kotlin
// Wrong
fun main() {
    val price = 100
    println("Total cost: $price * 2")
}

// Correct
fun main() {
    val price = 100
    println("Total cost: ${price * 2}")
}
```

The wrong version compiles and runs, but it prints `Total cost: 100 * 2` instead of `Total cost: 200`. A `$` followed by a name substitutes only that single variable; the rest (` * 2`) is treated as literal characters. To embed an expression that involves operators or method calls, use the `${...}` form. The fix is small but the bug it prevents is significant: the compiler cannot warn you here, so without curly braces a template quietly produces the wrong text.

**Error 2: Using Single Quotes for a String**

```kotlin
// Wrong
fun main() {
    val message = 'Hello, Kotlin!'
    println(message)
}

// Correct
fun main() {
    val message = "Hello, Kotlin!"
    println(message)
}
```

Kotlin uses double quotes for `String` literals and single quotes for `Char` literals. A `Char` is a single character (`'A'`, `'7'`, `'!'`), and a `String` is a sequence of characters (`"Hello"`). The wrong version does not compile: the compiler reports `Too many characters in a character literal.` because it expected exactly one character between the single quotes. The fix is to use double quotes for any text longer than one character. This differs from Python and JavaScript, where single and double quotes are interchangeable for strings.

**Error 3: Writing Statements Outside a Function**

```kotlin
// Wrong
println("Starting Catatku...")

fun main() {
    println("Hello, Catatku!")
}

// Correct
fun main() {
    println("Starting Catatku...")
    println("Hello, Catatku!")
}
```

The top level of a Kotlin file may contain declarations (functions, classes, properties), but not statements to execute. A `println` call written outside any function produces a series of `Syntax error: Expecting a top level declaration.` messages, one for each piece of the line the compiler could not place. The fix is to move the statement inside `main` (or inside another function that `main` calls), because code only runs when a function containing it is called.

## 9. Solutions

Try the exercises yourself first, then check the solutions below.

**Solution for Exercise 1:**

Store the name and birth year in variables, then let string templates build the three lines. The third line computes the age inside `${...}`:

```kotlin
fun main() {
    val name = "Budi Santoso"
    val birthYear = 1990
    println("Name: $name")
    println("Born in: $birthYear")
    println("Age in 2026: ${2026 - birthYear}")
}
```

Save and run.

Output:

```text
Name: Budi Santoso
Born in: 1990
Age in 2026: 36
```

The first two lines use the short `$name` form because each embeds a single variable. The third line needs the curly-brace form because `2026 - birthYear` is an expression with an operator; without the braces you would get the literal text `1990` followed by ` - birthYear`, the same bug as Error 1 above.

**Solution for Exercise 2:**

Defining a top-level function alongside `main` lets you organize logically related output into named units. The function takes no arguments and returns nothing, so the signature is `fun printTaskHeader()` with no parameter list filled in and no return type specified (the default return type when omitted is `Unit`, Kotlin's name for "no useful return value").

```kotlin
fun printTaskHeader() {
    println("===========================================")
    println("        Catatku Task List Demo             ")
    println("===========================================")
}

fun main() {
    printTaskHeader()
    println("[ ] 1. First task")
    println("[ ] 2. Second task")
}
```

Save and run.

Output:

```text
===========================================
        Catatku Task List Demo             
===========================================
[ ] 1. First task
[ ] 2. Second task
```

The function `printTaskHeader` is declared at the top level (no surrounding class), the same way `main` is declared. Both functions are visible throughout the file without any explicit linking. Calling a function is done with the function name followed by parentheses; even functions that take no arguments require the parentheses in the call site (`printTaskHeader()`), because the parentheses are how Kotlin distinguishes "call this function" from "reference this function as a value". We will see the value-as-a-function distinction more clearly when we cover lambdas in Lesson 13.

The order of function declarations does not matter in Kotlin. We declared `printTaskHeader` before `main` in the example above, but the program would work identically if we put `main` first and `printTaskHeader` after. Kotlin reads the entire file before deciding what each name refers to, so functions can call each other regardless of declaration order. This differs from C and many older languages where declarations had to come before uses; Kotlin is more like Java, Python, or JavaScript in this respect.

A subtle but important habit forms here: organize related code into named functions even when the functions are short. The five-line `printTaskHeader` could have been three `println` calls inline in `main`, but pulling them into a named function makes `main` easier to read and gives the operation a name we can reuse. This is the foundation of the refactoring we will do throughout the course: when something is worth doing, give it a name.

## 10. Understanding Top-Level Functions

One of Kotlin's quietly significant decisions is to allow functions at the top level of a file, with no enclosing class. Java does not allow this; every Java function must be a method of some class, even when the class is just a container for static utility methods (`public class Utils { public static int add(int a, int b) { ... } }`). Kotlin removes this requirement and lets you write `fun add(a: Int, b: Int): Int = a + b` directly at the top level. Understanding why this matters explains a lot about Kotlin's design philosophy.

Wrapping every function in a class adds noise without adding meaning when the function does not actually represent a method of an object. Mathematical helpers like `add` or `square`, parsing functions like `parseInt`, or output functions like `println` are not methods of a particular thing; they are operations that work on whatever you pass them. Forcing them into a class hierarchy is a workaround for the lack of top-level support, not a design choice that helps anyone. Kotlin treats this as a fixable problem: top-level functions exist, are public by default, and can call each other freely within the same file or across files in the same package.

The compiler still produces JVM bytecode that conforms to Java's "everything is a class" model. Behind the scenes, top-level functions in `Main.kt` are compiled into static methods on a synthetic class called `MainKt` (the file name with `.kt` replaced by `Kt`). This is why the `application { mainClass.set("MainKt") }` line in `build.gradle.kts` mentions `MainKt`: that is the class the compiler generates for `Main.kt`. From the JVM's perspective, nothing has changed; from your perspective, you do not have to think about classes when you do not need them, which is exactly the right tradeoff.

This same principle (give the developer a more direct way to express their intent, generate the boilerplate behind the scenes) shows up throughout Kotlin's design. Data classes generate `equals`, `hashCode`, and `toString`. Properties generate getters and setters. Sealed classes generate the closed type hierarchy. Default arguments generate the overloads. In each case, the tedious repetitive code that Java requires you to write is generated by the Kotlin compiler from a much shorter and clearer source. The benefits are real: less code to write, less code to read, fewer places for mistakes to hide, and a clearer picture of what the code is actually trying to do.

The cost of this approach is that beginners sometimes get confused about how Kotlin code interoperates with Java, because the JVM-level shape of Kotlin code is not quite what the source looks like. For most application work this never matters. When it does matter (during interop with Java codebases, or when reading stack traces with the synthetic class names), the small mental adjustment is worth it. The day-to-day productivity gain from being able to write top-level functions is significant, and over a long project the savings compound into thousands of lines of saved boilerplate.

## Next Up - Lesson 4

You now have a clear picture of the smallest meaningful Kotlin program. The `fun main()` function is the entry point, optionally taking an `Array<String>` of command-line arguments. The body of `main` runs when the program starts, and inside you can use `println` to write to the console with an automatic trailing newline, `print` for partial-line output, and string templates (`$variable` for simple cases, `${expression}` for arbitrary expressions) to embed values into strings. Comments come in three flavors: single-line with `//`, multi-line with `/* ... */`, and KDoc with `/** ... */` for API documentation. Top-level functions like `main` and any helpers you define do not need to be wrapped in a class, which is a major source of conciseness compared to Java.
