## 1. Before You Begin

Programming in any language requires a small but specific set of tools to be in place before the first line of code can be written. For Kotlin the requirements are pleasantly modest: a Java Development Kit (JDK) for the runtime, an editor that understands Kotlin (which in practice means IntelliJ IDEA, since it is made by the same company that makes Kotlin), and a build system to manage dependencies and compilation (which in practice means Gradle, since it is the standard for Kotlin projects). Once these three pieces are in place, you are ready to write and run Kotlin programs of any size.

This lesson walks you through installing each of those pieces, creating your first Kotlin project through IntelliJ's wizard, running the autogenerated Hello World, and exploring the project structure on disk so you understand what each file is for. Spending time on the directory layout now pays off later, because every Kotlin project you ever work on will have roughly the same shape, and recognizing that shape lets you orient yourself in any codebase quickly. By the end of the lesson, you will have a working environment, you will have run your first Kotlin program, and you will be ready to start writing real code in Lesson 3.

### What You'll Build

By the end of this lesson you will have a small but functional Kotlin project called `catatku` that contains the autogenerated Hello World code, a Gradle build file (`build.gradle.kts`), a Gradle settings file (`settings.gradle.kts`), and the standard directory layout that all Kotlin projects share. You will have run the project and seen "Hello World!" appear in the IDE's Run panel, which confirms that your environment is correctly set up. The project will be the foundation that every subsequent lesson builds on, so picking the name `catatku` now matches the application we are building across the whole course.

### What You'll Learn

- ✅ How to install a JDK on Windows, macOS, or Linux
- ✅ How to install IntelliJ IDEA
- ✅ How to create a new Kotlin Gradle project through the New Project wizard
- ✅ The role of `build.gradle.kts` and `settings.gradle.kts` in a Kotlin project
- ✅ The standard project directory layout (`src/main/kotlin`, `src/test/kotlin`)

### What You'll Need

- A computer running Windows, macOS, or Linux with at least 4 GB of RAM and a few gigabytes of free disk space
- Internet access for downloading the JDK and IntelliJ IDEA
- An hour or so of patient setup time (most of which is waiting for installers to finish)
- The orientation from Lesson 1, so you know what you are heading toward

## 2. Installing the JDK

Kotlin runs on the Java Virtual Machine (JVM), which is provided by a Java Development Kit. You do not need to learn Java to use Kotlin, but you do need a JDK installed so that the Kotlin compiler can produce JVM bytecode and the JVM can run it. Several JDK distributions exist; we will use Eclipse Temurin, which is free, open source, and well-maintained.

### Step 1: Choose a JDK Version

Kotlin 2.x supports JDK 8 and newer, but using a recent long-term-support release gives you the best experience. The current recommendation is JDK 17 or JDK 21, both of which are LTS releases. JDK 17 is fine for everything we will do in this course; JDK 21 has a few additional features that we will not use. If you already have a JDK installed from previous work and it is version 17 or newer, you can skip this section and use the existing one.

To check whether you already have a JDK, open a terminal (Command Prompt or PowerShell on Windows, Terminal on macOS, your shell of choice on Linux) and run:

```bash
java -version
```

If you see something like `openjdk version "17.0.x" 2024-xx-xx`, you have a usable JDK and can skip ahead. If you see "command not found" or a version older than 17, you need to install or upgrade.

### Step 2: Download Eclipse Temurin

Open your browser and navigate to the Eclipse Temurin download page at adoptium.net. The site detects your operating system and architecture and offers the appropriate installer. Choose JDK 17 LTS for the broadest compatibility. On Windows, download the `.msi` installer. On macOS, choose the `.pkg` installer for your processor type (Intel or Apple Silicon). On Linux, the `.deb` or `.rpm` package is easiest, or you can download the `.tar.gz` and extract it manually.

The download is around 200 megabytes. While it downloads, you can move on to the IntelliJ IDEA installation in parallel; the two tools install independently.

### Step 3: Install and Verify

Run the installer you downloaded. On Windows, accept the defaults; the installer adds the JDK to your `PATH` automatically. On macOS, run the `.pkg` and follow the prompts; macOS places the JDK at `/Library/Java/JavaVirtualMachines/temurin-17.jdk`. On Linux with a `.deb` file, install it with `sudo dpkg -i <filename>.deb`. On Linux with a `.tar.gz`, extract it to `/opt/jdk17` or your preferred location and add the `bin` directory to your `PATH` by editing `~/.bashrc` or `~/.zshrc` to include `export PATH="/opt/jdk17/bin:$PATH"`.

Verify the installation by opening a fresh terminal and running `java -version` again. You should see the version you just installed. If the version still shows the old one or "command not found", you may need to restart your terminal or, on Windows, log out and back in so that environment variable changes take effect. If you continue to have trouble, the Adoptium installation guide at adoptium.net/installation has detailed troubleshooting for each platform.

The JDK is now installed. The exact same JDK that runs Java code will also run any Kotlin code you write, because Kotlin compiles to JVM bytecode and uses the JVM as its runtime. This is what we mean when we say Kotlin "runs on the JVM": the JDK is the engine, and Kotlin is one of several languages that produce code the engine can run.

## 3. Installing IntelliJ IDEA

IntelliJ IDEA is the editor of choice for Kotlin development. It is made by JetBrains, the same company that created Kotlin, and it has the deepest, most polished Kotlin support of any editor available. Since version 2025.3, JetBrains ships IntelliJ IDEA as a single download: the core features, including full Kotlin and Gradle support, are free to use, and a paid subscription only unlocks extra tools for enterprise frameworks like Spring. The free features are everything you need for this course and for most personal projects.

### Step 1: Download IntelliJ IDEA

Navigate to jetbrains.com/idea/download in your browser. The page detects your operating system and offers the matching installer. Click the Download button. You do not need to start a paid subscription or trial; when the IDE asks on first launch, simply keep using the free features. The download is around 700 megabytes, so it may take a few minutes depending on your connection.

### Step 2: Install

Run the installer. On Windows, the installer offers options like "Add 'Open Folder as Project'" to the right-click menu and "Add launchers dir to the PATH"; both are useful and can be enabled. On macOS, drag the IntelliJ IDEA app to your Applications folder. On Linux, extract the `.tar.gz` to `/opt/idea` (or another location) and run `bin/idea.sh` to launch.

The first time you launch IntelliJ IDEA, it asks a few one-time questions: whether to import settings from a previous installation (choose "Do not import settings" if this is your first time), and which UI theme to use (Darcula is the default dark theme; Light is the default light theme; pick whichever is easier on your eyes). After these questions, you arrive at the Welcome screen, which is where you will create new projects from now on.

### Step 3: Verify Kotlin Support

Kotlin support is built into IntelliJ IDEA out of the box; you do not need to install any plugins. To confirm, look at the New Project wizard you will use in the next section: Kotlin should appear as a project type in the left sidebar without any plugin installation. If for some reason Kotlin is missing, you can verify the Kotlin plugin is enabled by going to Settings (or Preferences on macOS) > Plugins > Installed and confirming that "Kotlin" is in the list and checked. In a fresh installation it always is, so this check is just defensive.

The IDE also wants to know about your JDK so it can compile Kotlin programs. This usually happens automatically when you create your first project, but you can verify by going to File > Project Structure > Platform Settings > SDKs. There should be at least one entry for the JDK you installed in the previous section. If the list is empty, click the plus button and point IntelliJ at your JDK installation directory.

## 4. Creating Your First Kotlin Project

Now we use IntelliJ IDEA to create a new Kotlin project. The wizard sets up the directory layout, the build files, and a small Hello World example, all of which we will examine afterward.

### Step 1: Open the New Project Wizard

From the IntelliJ Welcome screen, click "New Project". A dialog opens with project type categories on the left. Click "Kotlin" in the left sidebar. The right side now shows project configuration options.

In the right panel, fill in the fields. Set the Name to `catatku`. Set the Location to wherever you want to keep your code; the default is usually a folder like `~/IdeaProjects/catatku` or `C:\Users\<You>\IdeaProjects\catatku`. Leave the Language as Kotlin and the Build system as Gradle (this is the default). For JDK, select the JDK 17 (or newer) you installed in Section 2. For Gradle DSL, select Kotlin (so your build script will be in Kotlin rather than Groovy; this is becoming the standard and is what we will use throughout). Leave the other options at their defaults unless you have a specific reason to change them.

### Step 2: Click Create

Click the Create button. IntelliJ opens the new project and immediately starts a process called "Gradle sync", which downloads any dependencies declared in the build file and indexes the project. The first time this happens it can take several minutes because Gradle is downloading itself, the Kotlin compiler, and the standard library, all of which it caches locally for future projects to share. Subsequent project creations are much faster because the cache is already populated.

You will see a progress bar at the bottom of the IDE window labeled "Sync" or "Importing Gradle project". Wait for it to complete. Once the sync finishes, the project tree on the left side of the IDE shows the project structure, and you are ready to run code.

### Step 3: Locate the Hello World

Look at the project tree on the left. Expand the `catatku` folder, then `src`, then `main`, then `kotlin`. You should see a single file called `Main.kt` inside. Double-click it to open it in the editor. The contents look something like this:

```kotlin
fun main() {
    println("Hello World!")
}
```

That is a complete, runnable Kotlin program. The `fun main()` declares the entry point of the program (where execution starts), and the `println("Hello World!")` line prints the text to the console. We will examine the syntax in detail in Lesson 3; for now, the goal is just to confirm the project works.

To run it, click the small green triangle (the Run icon) in the gutter next to the `fun main()` line. A menu may appear; choose "Run 'MainKt'". The first run takes a few seconds because Gradle compiles the project. When it finishes, a "Run" panel opens at the bottom of the IDE. Among the build messages, you will find the line printed by the program.

Output:

```text
Hello World!
```

Congratulations: you have run your first Kotlin program. The IDE also reports that the process finished with exit code 0, which is its way of telling you the program finished normally without errors. If you see any other output (a stack trace, an error about JDK not found, anything red), the section in the next paragraph explains how to diagnose common problems.

If running fails, the most common causes are a misconfigured JDK (verify File > Project Structure > Project SDK is set to your installed JDK), a Gradle sync that did not complete (look for an "Import Gradle Project" link in the bottom right and click it), or simply not having waited long enough for the initial sync to finish. The IDE's bottom-left status area shows what it is currently doing; if it says "Indexing" or "Resolving dependencies", let it finish before trying to run.

## 5. The Project Structure on Disk

Now that the project runs, let us look at what is actually on disk. Understanding the layout is important because every Kotlin project you ever work on uses the same conventions, and recognizing them lets you navigate any codebase quickly.

### Step 1: Look at the Top-Level Files

Open a file explorer or terminal and navigate to the project folder (the location you chose during creation). At the top level you should see something like this:

```text
catatku/
├── .gradle/
├── .idea/
├── build/
├── gradle/
├── gradlew
├── gradlew.bat
├── settings.gradle.kts
├── build.gradle.kts
├── gradle.properties
└── src/
```

Each of these has a specific purpose. The `.gradle` directory contains caches and incremental build state for Gradle itself. The `.idea` directory contains IntelliJ-specific settings that should usually not be committed to version control. The `build` directory contains compiled output and is regenerated whenever you build the project, so it can be safely deleted at any time. The `gradle` directory and the `gradlew` and `gradlew.bat` scripts together make up the "Gradle wrapper", a small tool that lets you run Gradle commands without needing Gradle installed system-wide. The wrapper downloads and uses the exact version of Gradle that this specific project expects, which is enormously useful for sharing projects between team members.

The two files that matter most for daily work are `settings.gradle.kts` and `build.gradle.kts`. The settings file tells Gradle the name and structure of the project at a high level, and the build file declares the project's dependencies, plugins, and build configuration. Open both of them now to see what they look like.

### Step 2: Read settings.gradle.kts

Click `settings.gradle.kts` in the project tree (or open it from the file explorer). The file looks something like:

```kotlin
plugins {
    id("org.gradle.toolchains.foojay-resolver-convention") version "0.8.0"
}

rootProject.name = "catatku"
```

The `plugins` block declares plugins for the settings level (the foojay resolver helps Gradle download JDKs automatically if needed). The `rootProject.name = "catatku"` line gives the project a name, which is the same name you typed in the wizard. For a single-project build like Catatku, this file barely changes; for multi-module projects it grows to include `include("module-name")` lines for each module. We will not need multi-module setups in this course.

### Step 3: Read build.gradle.kts

Now click `build.gradle.kts`. This is the file you will edit most often, because it declares dependencies. The default content looks like this (the version numbers may differ slightly depending on your IntelliJ IDEA version):

```kotlin
plugins {
    kotlin("jvm") version "2.0.0"
    application
}

group = "org.example"
version = "1.0-SNAPSHOT"

repositories {
    mavenCentral()
}

dependencies {
    testImplementation(kotlin("test"))
}

application {
    mainClass.set("MainKt")
}

tasks.test {
    useJUnitPlatform()
}

kotlin {
    jvmToolchain(17)
}
```

This course was written and tested with Kotlin 2.0.0, the version shown in the `plugins` block above. If the wizard generated a newer 2.x version, everything in the course still works, but you can change the version to `2.0.0` if you want your output to match the lessons exactly.

Walk through what each section does. The `plugins` block declares which Gradle plugins this project uses; `kotlin("jvm")` enables Kotlin compilation for the JVM, and `application` lets you run the project with `./gradlew run`. The `group` and `version` are metadata used when publishing artifacts, which we will not do in this course but which Gradle expects to be set.

The `repositories` block tells Gradle where to look for dependencies; `mavenCentral()` is the standard Java/Kotlin artifact repository and is sufficient for almost everything you will ever need. The `dependencies` block declares external libraries that the project depends on; the wizard added `kotlin("test")` as a test-only dependency so we can write tests in Lesson 21.

The `application { mainClass.set("MainKt") }` line tells the application plugin which class contains the `main` function. Kotlin's `fun main()` in `Main.kt` becomes a class called `MainKt` after compilation (Kotlin generates a class for top-level functions, named after the file with "Kt" appended). The `tasks.test { useJUnitPlatform() }` line configures the test framework, and `kotlin { jvmToolchain(17) }` tells the Kotlin plugin to use JDK 17 for compilation.

Each line of `build.gradle.kts` is doing something specific, and you can edit this file to add or remove dependencies, change versions, or configure plugins. We will edit it in Lesson 20 to add the kotlinx.serialization library and again in Lesson 21 to confirm the test framework. For now, just notice the structure; you do not need to memorize anything.

### Step 4: Look at the src Directory

Navigate into `src` in your file explorer. You see two subdirectories: `main` and `test`. Inside `main` is `kotlin` (and possibly `resources`). Inside `test` is also `kotlin` (and possibly `resources`). This is the standard "convention over configuration" layout used by every Maven and Gradle JVM project.

The `src/main/kotlin` directory holds the actual production source code. The `src/main/resources` directory (if present) holds non-code resources like configuration files. The `src/test/kotlin` directory holds test code. The `src/test/resources` directory holds test resources. By convention, anything in `main` is part of the runtime application, and anything in `test` is compiled and run only during testing.

When you create new Kotlin files for Catatku in later lessons, they will go in `src/main/kotlin`. When you create test files in Lesson 21, they will go in `src/test/kotlin`. The project tree in IntelliJ presents these directories in a friendly way, hiding some of the deeper folders by default and emphasizing the ones you actually care about, but underneath the cleaner presentation is exactly the standard layout.

## 6. Run and Test

You have already run the Hello World once. Run it a few more times, modify it slightly, and observe what happens. This builds the muscle memory of the edit-run cycle that you will use thousands of times across your Kotlin career.

### Step 1: Modify the Greeting

Open `Main.kt` and change `"Hello World!"` to `"Hello, Catatku!"`. Save the file (Ctrl+S on Windows/Linux, Cmd+S on macOS) and click the green run triangle next to `fun main()` again. The Run panel at the bottom now shows the new greeting.

Output:

```text
Hello, Catatku!
```

Notice that you did not have to recompile manually or restart anything. IntelliJ detected the change, recompiled the file in the background, and ran the new version. This tight feedback loop is one of the things that makes IDE-based development pleasant; the IDE handles the build steps invisibly so you can focus on the code.

### Step 2: Add a Second Line

Add a second `println` line to the function so it looks like this:

```kotlin
fun main() {
    println("Hello, Catatku!")
    println("Setup complete.")
}
```

Save and run again. The output now has two lines.

Output:

```text
Hello, Catatku!
Setup complete.
```

Each `println` produces one line of output followed by a newline. Multiple `println` calls in sequence produce multiple lines in order. This is exactly what you would expect from any programming language, but seeing it work in your own setup confirms that everything is wired correctly.

### Step 3: Run from the Command Line

The IDE's run button is convenient, but you can also run the project from a terminal using the Gradle wrapper. Open a terminal, navigate to the project root (`cd ~/IdeaProjects/catatku` or your equivalent), and run:

```bash
./gradlew run
```

On Windows, use `.\gradlew.bat run` instead. The first time, Gradle prints download progress as it fetches itself (the wrapper script downloads the actual Gradle distribution on first use). After that, it compiles your project and runs the `application` plugin's `run` task, which executes the `main` function. You should see the same lines as in the IDE, surrounded by some extra Gradle build output.

Output:

```text
> Task :run
Hello, Catatku!
Setup complete.

BUILD SUCCESSFUL in 2s
2 actionable tasks: 2 executed
```

The build time and the task counts can differ on your machine. If you only want to see what your program prints, add the `-q` (quiet) flag, which hides Gradle's own messages:

```bash
./gradlew run -q
```

Output:

```text
Hello, Catatku!
Setup complete.
```

From now on, every `Output:` block in this course shows only what the program prints, the same lines you see with `./gradlew run -q` or in the IDE's Run panel.

The command-line approach is what build servers and deployment scripts use, so knowing it exists is useful even if you mostly work in the IDE day-to-day. For most of this course we will use the IDE's run button because it is faster, but at any point you can drop into the terminal and use Gradle directly if you prefer.

## 7. Fix the Errors in Your Code

Three setup mistakes are common for newcomers and worth recognizing.

**Error 1: Asking Gradle for a JDK You Do Not Have**

```kotlin
// Wrong (build.gradle.kts): only JDK 17 is installed
kotlin {
    jvmToolchain(11)
}

// Correct (build.gradle.kts): match the JDK you installed
kotlin {
    jvmToolchain(17)
}
```

The `jvmToolchain` line tells Gradle which JDK version must compile and run the project. If you change it (or copy a build file from another project) to a version that is not installed, the build stops before compiling anything and Gradle reports `Cannot find a Java installation on your machine ... matching: {languageVersion=11, ...}`. The fix is to keep the number in `jvmToolchain` equal to a JDK you actually have, which in this course is 17 or newer. Also check File > Project Structure > Project in IntelliJ IDEA, because most version-related setup pain comes from a mismatch between what the build file expects and what the IDE has selected.

**Error 2: Writing Groovy Syntax in a Kotlin DSL Build File**

```kotlin
// Wrong (build.gradle.kts): Groovy style, no parentheses
dependencies {
    testImplementation kotlin("test")
}

// Correct (build.gradle.kts): Kotlin DSL calls functions with parentheses
dependencies {
    testImplementation(kotlin("test"))
}
```

Gradle build scripts come in two flavors: Groovy (in `build.gradle`) and Kotlin (in `build.gradle.kts`). Many tutorials on the internet still use Groovy, where parentheses are optional. In a `.kts` file, the same line fails with a `Script compilation error` that points at the line and complains about an `Unresolved reference`. The fix is to write every dependency as a function call with parentheses. Throughout this course we use the Kotlin DSL exclusively, which is also why you should choose Kotlin as the Gradle DSL in the New Project wizard.

**Error 3: Putting Source Files Outside src/main/kotlin**

```text
// Wrong: Greeting.kt sits in the project root
catatku/
├── Greeting.kt
└── src/main/kotlin/Main.kt

// Correct: every source file lives under src/main/kotlin
catatku/
└── src/main/kotlin/
    ├── Greeting.kt
    └── Main.kt
```

Kotlin source files must live under `src/main/kotlin` (or `src/test/kotlin` for tests) for Gradle to find them. A file in the project root is simply ignored, so if `Main.kt` calls a function declared in that file, the compiler reports `Unresolved reference 'greet'.` even though you can see the function on screen. The fix is to move the file into `src/main/kotlin`. As a habit, always create new Kotlin files by right-clicking on `src/main/kotlin` in the project tree and selecting New > Kotlin Class/File, which starts you off in the right location.

## 9. Solutions

Try the exercises yourself first, then check the solutions below.

**Solution for Exercise 1:**

Replace the body of `main` with three `println` calls, one for each line you want to print:

```kotlin
fun main() {
    println("My name is Rina.")
    println("My favorite programming language so far is Python.")
    println("I hope to build my own command-line tools with Kotlin.")
}
```

Save and run.

Output:

```text
My name is Rina.
My favorite programming language so far is Python.
I hope to build my own command-line tools with Kotlin.
```

Each `println` prints its text and then moves to a new line, so the three lines appear in exactly the order you wrote the calls. Put your own name, language, and goal inside the quotes; the structure stays the same.

**Solution for Exercise 2:**

Change `println` to `printlin` and run:

```kotlin
fun main() {
    printlin("Hello, Catatku!")
}
```

The program does not run at all. The build stops at the compile step, and the Run panel shows the compiler message `Unresolved reference 'printlin'.` together with the file name, line, and column (`Main.kt:2:5`). "Unresolved reference" means the compiler looked for something named `printlin` and found nothing with that name. IntelliJ IDEA also underlines the word in red before you even run the program. Change the name back to `println`, run again, and the greeting appears as before. Reading the message, location, and name in a compile error is a skill you will use in every lesson.

**Solution for Exercise 3:**

Creating a second file teaches you that Kotlin functions are visible across files in the same package without any explicit import, as long as both files are at the top level (no `package` declaration). Right-click on `src/main/kotlin` in the project tree, select New > Kotlin Class/File, and name the file `Greeting`. The IDE creates `Greeting.kt`. Inside, write:

```kotlin
fun greet(name: String) {
    println("Hello, $name!")
}
```

The function declaration `fun greet(name: String)` says the function takes one parameter named `name` of type `String`. The body uses string template syntax (`$name`) to interpolate the parameter into the printed text. We will cover string templates and parameter declarations in detail in Lessons 3 and 6 respectively, but for this exercise the syntax is simple enough to use without full understanding.

Now open `Main.kt` and modify the `main` function to call `greet`:

```kotlin
fun main() {
    greet("Kotlin")
}
```

Save both files and run `Main.kt`.

Output:

```text
Hello, Kotlin!
```

The two files do not need any explicit connection: because both `greet` and `main` are top-level functions without a `package` declaration, they share an implicit "default package" and can call each other directly. In a multi-package setup you would need an `import` statement, but we will not introduce packages until Lesson 17.

This exercise demonstrates one of Kotlin's small ergonomic advantages over Java: you can have multiple top-level functions across multiple files without wrapping them in classes, and they all see each other if they share a package. In Java the equivalent code would require both functions to be `public static` methods inside classes, which is more ceremony than the situation deserves. Kotlin's approach matches what most programmers actually want: small utility functions that live where they are most discoverable, not buried inside a `Utility` class that nobody can find.

## 10. Understanding the Build System

Newcomers often wonder why Kotlin needs a build system at all when other languages let you just compile and run a single file. The answer has to do with how JVM projects manage dependencies and how Kotlin fits into the broader Java ecosystem.

A typical Kotlin project depends on libraries: the Kotlin standard library, third-party libraries like kotlinx.serialization, test frameworks like JUnit, logging libraries, and so on. Each of these libraries is itself a JAR file (a Java archive containing compiled classes), and each one might depend on still more libraries. Managing this graph of dependencies by hand is impossible for any non-trivial project. A build system like Gradle declares the dependencies in a build file, downloads them from a repository like Maven Central, organizes them on the classpath, and hands the assembled bundle to the compiler and runtime. You write `dependencies { implementation("org.jetbrains.kotlinx:kotlinx-serialization-json:1.7.1") }` and Gradle takes care of fetching that artifact, finding everything it depends on, and putting it all where the compiler expects.

Beyond dependency management, the build system also handles compilation, packaging, testing, running, and deployment. Each of these is a "task" in Gradle terminology, and the build file configures how each task should run. The convention-over-configuration approach means you usually do not have to specify much; Gradle assumes sensible defaults like "source files are in `src/main/kotlin`" and "tests are in `src/test/kotlin`" so that you only override what genuinely differs in your project. This is why the autogenerated `build.gradle.kts` is short despite enabling so much functionality: most of the work is done by conventions baked into the plugins.

Why specifically Gradle rather than Maven or some Kotlin-specific tool? Maven is older and more common in Java codebases, but its XML-based build files are verbose and hard to extend. Gradle uses a real programming language for build scripts (originally Groovy, now also Kotlin), which makes it more flexible and more pleasant to read once you are used to it. The Kotlin team, JetBrains, the Android team, and most modern Kotlin libraries have all standardized on Gradle as the recommended build system. Using anything else is possible but means swimming against the current of documentation and community expectations. So we use Gradle, and specifically the Kotlin DSL flavor of Gradle, because that is the path of least resistance.

The Gradle wrapper deserves a separate mention because it is one of the genuinely good ideas in the JVM build world. The `gradlew` and `gradlew.bat` scripts in your project root let anyone build the project without first installing Gradle system-wide; the scripts download the exact version of Gradle the project was tested with, cache it locally, and use it for all builds. This is why we never said "install Gradle" earlier in this lesson. The wrapper is enough, and it ensures that everyone working on the project uses the same build tool version, which prevents a whole class of "works on my machine" bugs caused by version drift between team members. Always use the wrapper rather than a system-installed Gradle for any project that has one.
